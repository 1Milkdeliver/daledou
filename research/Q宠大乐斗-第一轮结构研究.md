# Q宠大乐斗第一轮结构研究

日期：2026-08-20  
范围：研究落地清单、脱敏数据包、接口字典、接口限制报告、最新页面快照与差分实验索引。  
边界：本报告不包含账号、Cookie、原始 HTML、私有 URL 或可执行接口参数；仅用于原创桌宠 + MCP 游戏设计。

## 结论摘要

Q宠的底层不是一个统一的大世界循环，而是一个由服务端文字页组织的“入口网络”：首页把大量常驻、赛季、社交、成长、付费和领取入口聚合；每个入口由服务端判断前置并立刻结算或返回下一选择页。其长期留存来自自动战斗的可读战报、层层成长、每日可领取资源和异步关系，而不是实时操作。

对原创项目最有价值的取舍是：保留“状态 → 轻选择 → 服务端结算 → 高光 → 可见变化”，舍弃入口爆炸、多币种堆叠和以 URL 参数承载动作的历史架构。

## 1. 系统层级总览

```text
角色身份/外观/成就
  ├─ 基础状态：等级、体力/活力、阅历、战力
  ├─ 自动战斗：历练、好友/BOSS、竞技、塔、副本、赛季
  ├─ 战斗构筑：武器/技能、魂珠/镶嵌、助阵、佣兵
  ├─ 长期养成：强化、铁匠铺、星盘、神魔录、附魔、经脉等
  ├─ 资源经济：日常奖励、活动、商店、兑换、多类积分/材料
  └─ 异步关系：好友、师徒、帮派、侠侣、排行、名人堂
```

观察样本中的首页入口、背包物品类别和成长线数量已远超轻量用户一次能处理的范围。这是 Q宠的内容厚度，也是新用户理解成本的主要来源。

## 2. 成长树总览

| 层 | 代表页面/系统 | 核心机制 | 对玩家的感受 | 原创 MVP 取舍 |
| --- | --- | --- | --- | --- |
| 基础成长 | 等级、经验、体力/活力 | 行动获得经验，资源限制行动频率 | 今天比昨天更强 | 保留，字段极少 |
| 战斗能力 | 武器/技能、强化 | 材料消耗、成功率分级、升星/觉醒 | 选择与赌成长 | 首发仅保留装备 + 有限能力；前期必成 |
| 构筑 | 魂珠/镶嵌、星盘、助阵 | 组合、属性、摘除/升级 | 配装造成差异 | MVP 只做一种可替换构筑槽 |
| 长线保底 | 神魔录、佣兵 | 品质、碎片、祝福值/保底、资质 | 长期追逐与收集 | 后置；不要首发多条碎片线 |
| 工艺成长 | 铁匠铺、附魔、神匠坊 | 进度条、材料、相邻/合成规则 | 制作与精炼 | 后置为赛季或收藏内容 |
| 身份展示 | 徽章、荣耀、名人堂 | 目标、品质、展示、部分加成 | 被看见、长期成就 | MVP 做纯外观/图鉴，不加战力 |

### 成长设计启示

1. 一条成长线应改变战报中可解释的行为，而非只增加不可见战力。
2. Q宠把外观/成就与数值部分绑定；我们的外观应尽量横向表达，避免收藏变成战力门槛。
3. 保底、碎片、升星、宝石和多种材料同时存在会形成材料债。MVP 只保留一条深度线、两条表达线。

## 3. 活动模板对照表

| 模板 | 状态机 | Q宠样例类别 | 用户动力 | 我们的改造 |
| --- | --- | --- | --- | --- |
| 每日领取 | 可领取 → 已领取 → 次日刷新 | 登录礼、活跃礼包、周礼包 | 零成本回访 | 只保留一个“已结算”卡片，不做领取清单 |
| 免费机会 | 免费次数 → 随机结果 → 次数耗尽 | 每日抽取/宝箱 | 惊喜、稀有度展示 | 用可解释掉落 + 保底，不与付费胜率绑定 |
| 自动 PvE | 目标 → 门槛检查 → 战斗 → 战报/掉落 | 历练、塔、副本 | 轻选择、看结果 | MVP 的核心；行动可在几十秒内结束 |
| 连续目标 | 第 N 天状态 → 达成 → 奖励 | 许愿/连续任务 | 形成回访节奏 | 允许中断与补救，避免强迫每日上线 |
| 报名赛季 | 报名 → 等待 → 异步结算 → 领奖 | 排名/周赛/组织赛 | 身份、竞争、期待 | 后置；首发以协战/战报卡替代 |
| 兑换商店 | 获得积分 → 选择兑换 → 扣除 → 入账 | 竞技/组织/副本商店 | 明确目标 | 只保留一种非付费活动积分 |

## 4. 战报数据结构

现有完整战报可归纳为：

```text
BattleFact
  battle_id / mode / scene
  participants: { actor, opponent, pre_battle_state }
  rounds[]:
    - round_number
    - actor_action / skill_or_weapon
    - target
    - damage_or_effect
    - trigger_tags: [crit, passive, counter, ...]
    - hp_after
  outcome: win / lose / terminate
  rewards[]
  resource_delta[]
  warnings_or_next_action
```

### 确定性/随机性分层

| 层 | 观察结论 | 我们的设计 |
| --- | --- | --- |
| 确定输入 | 角色状态、装备、技能、目标、次数/门槛 | 服务器快照中明确返回 |
| 服务端过程 | 回合、伤害、触发、HP 变化由服务器生成 | 服务器结算并保存事实 |
| 可见随机 | 暴击、技能触发、抽取品质、掉落 | 标注触发原因/稀有度；设概率上限和保底 |
| 叙事包装 | 场景文案、战斗描述、结果高光 | 本地模板或用户 Agent 生成；不得改变事实 |

不能由当前样本断言完整战斗公式或伪随机算法；但足以确认“事实先结算、叙事后呈现”是正确分层。

## 5. 每日固定产出与差分实验

实验记录当前能回链到 before/after 快照。已知样本显示：

| 行动类型 | 已观察结果 | 证据强度 | 研究含义 |
| --- | --- | --- | --- |
| 已领取/重复类免费操作 | 角色主快照和可做入口未出现变化 | 单样本 | 可能有已领取守卫；不能泛化为所有操作幂等 |
| 师徒/贡献领取类 | 两个样本未见角色主字段变化 | 两样本 | 奖励可能落在未抽取字段或操作可能被守卫，需要补背包/贡献字段 |
| 每日奖励类 | 观察到一个货币字段变化 | 单样本 | 每日领取是明确的服务器资产变更，应有账本记录 |

实验方法正确，但目前不足以形成“每日固定产出表”。后续每类行动至少需要：前置、是否执行、结算文本、角色/背包/任务三类差分、重复执行结果。

## 6. 旧文字端的数据交互教训

公开的接口矩阵显示大量入口共享少数通用容器，且动作与视图在同一文字页协议中混杂。限制报告进一步显示：页面实时渲染、错误语义弱、部分动作有频率限制、历史记录易失。

### 借鉴

- 服务端权威返回状态与结果；
- 每日领取存在防重思想；
- 轻量、服务端渲染的结果页适合弱设备与碎片时间。

### 不应复制

- 用 GET/链接参数触发资产变更；
- HTTP 成功却以文案判断失败；
- URL 暴露用户标识；
- 客户端靠页面文案推断动作和资源；
- 把动作、查询、错误和结算混在一个 HTML 返回中。

我们的服务端应采用：`GET snapshot`、`GET preview`、`POST command(commandId, revision)`、`GET operation`、`settlement + ledger`；MCP 仅映射这些受限能力。

## 7. 对桌宠 + MCP MVP 的具体映射

| Q宠结构 | 原创桌宠实现 |
| --- | --- |
| 首页百余入口 | 宠物卡只显示下一步、刚结算、成长、协战四块 |
| 自动战斗文字战报 | 服务器返回结构化事实；本地生成短高光 |
| 多层永久养成 | 基础成长 + 一种构筑 + 外观收藏 |
| 每日任务瀑布 | 无硬日常上限；按可做/可结算事件推荐 |
| 好友/师徒/组织入口 | 首发异步协战与分享卡；无实时聊天/公会 |
| 多货币商店 | 首发最多一类常规资源、一类成长材料、一类外观材料 |

## 8. 下一轮最有价值的数据

1. 同类战斗在不同构筑下的 3 份完整战报；
2. 一次邀请/协战的双方前后差分；
3. 连续 7–14 天同时间快照；
4. 每日领取、免费抽取、兑换各 3 次以上的结构化实验；
5. 新手/回归玩家的解锁与失败引导样本。

## 来源与可信度

- 快照页与差分实验：本机实测，适合描述已观察到的界面和结果结构；
- 接口字典：任务代码静态分析，不能等同官方接口文档；
- 限制报告：研究环境观察，不能推出生产服务的完整安全策略；
- 所有概率、长期经济和通用规则均需多日/多样本验证。
