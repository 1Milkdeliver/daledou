## 一、用户端数据结构（已可解析 ★）

### 1.1 实体模型（工具：entity_model.py → log/account_model.json）

从 19 页快照解析出的账号实体（首次提取实测）：

| 实体 | 数量 | 字段 | 来源页 |
| --- | --- | --- | --- |
| 角色 | 1 | 等级/经验/体力/活力/战力/斗豆/斗币/鹅币/活跃度 | index |
| 背包物品 | 10+/页（18 页） | 名称/数量 | store |
| 武器/技能 | 19 | 名称/等级/成功率（必成/低/中/高） | viewupdate |
| 佣兵 | 9 | 名称/碎片进度 (x/150) | newmercenary |
| 星石 | 9 | 等级/名称/属性（速度+2、闪避+2.0%） | astrolabe |
| 徽章 | 8 | 品质（青铜~钻石）/阶/名称 | achievement |
| 成就 | 多 | 目标/进度/封赏 | glory |
| 徒弟 | 2 | 名称/等级/乐斗状态 | disinfo |
| 好友侠/BOSS | 8 | 名称/等级/已乐斗 | friendlist |
| 战报 | 5-10 | 结果/回合/技能/HP（当天易失） | info + viewfight |

**实体关系（推断）**：角色 → 装备/武器/技能/佣兵/星石/神魔录/经脉（战斗成长面）
+ 背包（资源池）→ 兑换/强化/附魔（消耗面）→ 战斗力（总指标）→ 社交（好友/师徒/帮派/侠侣）
→ 每日任务/活跃度（节奏面）。

### 1.2 页面模板结构 ★

所有页面共用骨架（XHTML Mobile 1.0）：
```
<head> 大乐斗 标题 + pgconvert.css/phone.css + pgconvert.js/midas.js </head>
<body>
  <div id="id">
    [顶部: 公告/活动入口（全部活动链接）]
    [主体: 【页面名】 + 内容块（数据 + 操作链接）]
    [底部: 商店/兑换/背包/强化/镶嵌/经脉/佣兵/帮派... 全局导航]
    [世界喇叭: 实时播报]
  </div>
</body>
```
- 主体内容以 `<p>`/`<br/>` 分行，链接为 `cmd=xxx&op=yyy` 内联参数
- 底部全局导航固定 → 从任何页面都能跳到系统页（我们的快照天然覆盖）

### 1.3 状态令牌字典 ★（客户端状态机）

页面中出现的**状态标记** = 客户端决策输入：

| 令牌 | 含义 | 出现页 |
| --- | --- | --- |
| 已乐斗 / 已领取 / 已兑换 / 已交易 | 今日已做（幂等守卫触发） | friendlist/exp/fac_corp |
| 体力值不足 / 活力不足 | 资源门槛 | cfight/历练 |
| 免费挑战次数已用完 | 次数门槛 | arena |
| 成功报名 / 已报名 | 报名态 | 武林/侠侣 |
| 第 x/y 页 | 分页位置 | store/friendlist |
| 今日分享次数：x/5 | 每日计数 | sharegame |
| 连续许愿N天 | 跨日计数 | 许愿 |
| 未达成 / 未开通 | 等级门槛 | glory/幻境 |
| 刷新过于频繁 | 动作级限流 | 镖行天下 |
| 系统繁忙 | 通用错误（参数错/限流/故障） | 任意 |

> **价值**：这些令牌构成游戏的"客户端状态机"——把令牌清单整理全，
> 就等于拿到了自动化决策表；对桌宠游戏设计则是"状态反馈设计"的参考。

## 二、服务器层面（间接观测）

### 2.1 已确认事实 ★

| 项 | 结论 | 证据 |
| --- | --- | --- |
| 传输 | HTTP/1.1 + Apache + no-cache，恒 200 | 探测 |
| 鉴权 | 仅 Cookie；无 UA/Referer/CSRF 校验 | 探测 |
| 页面级限流 | 20 连发无拦截；服务器延迟 ~600ms 为天然限速 | 探测 |
| 动作级限流 | 存在（"刷新过于频繁"） | 日志 |
| 幂等守卫 | 每日领取有"已领取"防重 | exp/领取类页面 |
| 每日重置时间 | **疑似凌晨 6:00** | 许愿"明早6点后"、VIP 活动"早6点至" |
| 通用错误 | "系统繁忙" = 参数错/限流/故障统一页 | 探测 |
| GET 即执行 | 领取类操作都是 GET 触发 | exp 等 |

### 2.2 待验证实验 ⬜（都是安全的观测设计）

1. **日重置时刻确认**：凌晨 6:05 自动快照（比 22:00 多一次），对比"活跃度归零/体力回满/次数重置"。
   → 新增定时任务 `daledou-snapshot-6am`（每天 06:05），成本低、纯只读。
2. **会话失效特征**：cookie 过期时首页变什么（登录页/重定向/系统繁忙）→ 建立失效预警脚本。
3. **竞态守卫**：并发同时领取同一奖励 → 观察是否只到账一次（安全起见用每日奖励，且只在重置后测试一次）。
4. **延迟画像**：对三类接口（视图/领取/战斗）各测 10 次，建立延迟分布表 → 自动化预算依据。
5. **分页上限**：背包/好友列表逐页探测，确认实际页数（只读）。

### 2.3 刻意不做 ✋（账号风险 / 无研究价值）

- 高频爆破找限流阈值（>50 连发）
- 并发放大（并发 >10）
- 参数注入/越权测试（他人 uin、他人战报 id）
- 绕过守卫的重复领取尝试
- 伪造/篡改 cookie 或请求签名

## 四、未来异步协战数据契约（DSH 交接 · 任务4，2026-08-21）

> 研究问题：为原创项目的未来异步协战设计「冻结快照、双方零消耗、独立奖励、一次性幂等结算」的数据契约；
> 不研究实时聊天、公会或第三方接口自动化。

**来源范围与日期**：本机协战相关研究（原版异步交互观测）+ 接口层幂等/守卫研究 + 原创项目架构（04 档案），2026-08-21。
**观察量**：原版协战类交互的结构观测（好友/BOSS 组队、师徒贡献）+ 幂等守卫实测。
**证据等级**：页面显示 + 代码注释（原版）→ 契约设计为原创推断。

### 4.1 契约原则

| 原则 | 含义 | 防什么 |
| --- | --- | --- |
| 冻结快照 | 发起时冻结协战者角色快照（等级/构筑/战力），结算用快照不用实时状态 | 中途改号/改装的作弊与不一致 |
| 双方零消耗 | 被协战者不消耗任何资源，发起者也不为协战本身付费 | 拒绝参与、被薅资源 |
| 独立奖励 | 双方各自获得独立奖励（发起者正常奖、协战者协助奖），自动到账 | 分配争议 |
| 一次性幂等 | 同一协战事件只结算一次；重复请求/重放返回同一结果 | 重复刷奖、竞态双结算 |

### 4.2 数据契约（建议表结构）

```text
co_op_events（协战事件）
  co_op_id (uuid)            -- 事件唯一键，幂等键
  inviter_id / helper_id
  target_id / difficulty
  helper_snapshot_version    -- 冻结快照版本（见下）
  status(enum: pending|settled|expired)
  created_at / settled_at / ruleset_version

helper_snapshots（冻结快照，不可变）
  snapshot_id / player_id / level / build_hash / power / captured_at
  -- 一次性写入，结算时只读

co_op_settlements（结算，只写一次）
  settlement_id (= co_op_id) -- 幂等：存在即返回原结果
  inviter_reward / helper_reward
  battle_facts_hash          -- 结算事实哈希（防篡改）
  ledger_entries[]           -- 双方各自一条账本记录
```

### 4.3 幂等结算流程

```
1. POST /api/coop/invite {target, difficulty}  → 返回 co_op_id + helper 列表
2. 协战者确认（或到期自动）→ 服务器冻结双方快照 → status=pending
3. POST /api/coop/settle {co_op_id}
   - 若 settlement 已存在 → 返回原结果（幂等，不重算不重奖）
   - 否则 → 用冻结快照结算 → 写入 settlement + 双方 ledger → status=settled
4. 双方 GET /api/coop/{id} 查看结果（结果恒定）
```

### 4.4 可复用抽象结构

1. **幂等键 = 业务事件 id**（settlement_id = co_op_id），比客户端随机键更可审计
2. **结算事实哈希**：战斗事实 hash 入库，防"结算后再改叙事"的争议
3. **快照版本化**：helper_snapshot_version 支持规则升级后追溯
4. **奖励隔离**：发起/协助两套奖励池，互不侵蚀

### 4.5 不可迁移内容

实时聊天、公会/组队系统、第三方接口自动化、原版协战的社交压力机制（邀请轰炸/刷屏）。

### 4.6 待验证项

- 协战者离线时的事件超时/自动结算规则（pending → expired 时限）
- 奖励上限与防刷（每玩家每日协助奖励次数上限，仅防滥用、不惩罚正常参与）
- 快照与实时状态的偏差容忍（协战者结算前升级了怎么办 → 快照优先）

### 4.7 建议规则表字段

```text
co_op_id / inviter_id / helper_id / difficulty / status /
helper_snapshot_id / settlement_hash / inviter_reward / helper_reward /
ledger_ids[] / created_at / settled_at / ruleset_version
```
